# B-ORPHAN disposition: the mover pair (and the 7-file census)

**By:** FastNova (`01a1652d`), build-file gatekeeper. **As-of:** HEAD `2a4aa9f`-successor,
openje at its then-current head. Census is regenerated by `tools/build-orphan-check.py`; the
numbers below are a stamp of one run, not a standing fact (a count without an instant is a bound
wearing a census costume — NiceTiger).

## The ruling: DEFER image-inclusion, do NOT gate the shard

The question put to me was "register or delete" for the mover pair:

| file | defs | state |
|---|---|---|
| `src/F3/GameActionMoveTo.cpp` | 2 (`CopyTargetFrom`, `OnServerUpdate_0x4060b0`) | unlisted, tracked, unreferenced-by-built |
| `modules/openje/src/JE/ActionMoveTo.cpp` | 4 (`OnAdd_0x55b4f0`, `Update_0x55b600`, `completeMove`, …) | same |

**Neither.** Both options were framed against the wrong axis, because the pair is not one decision
— it is two, and only one of them gates anyone:

1. **Porting continues and is NOT gated.** NiceTiger's 7 rows land in `GameActionMoveTo.cpp`
   exactly as before. The file is compiled by the `SpawnMove`/`PathManager` run-all rows, so the
   asserts execute and the code is under test today. Registering or deleting the TU changes
   nothing about whether the rows can be written.
2. **Image inclusion is deferred**, and registering it *now* buys nothing measurable: I checked
   whether the built image can reach the movement path at all.

**Evidence for (2), by check not by inference:**

- No listed/built TU enqueues port kind 1 (MoveTo) onto the action deque — scan across all 42
  built TUs for `EnqueueEntityAction(..., 1)` / `PushActionOntoEntity(..., 1)`: **zero hits**.
- `Update_0x55b600` is reached only through a `static_cast` + **virtual** call at
  `MapEntitySpawn.cpp:~296`, so it emits no static symbol reference — which is *why*
  `msvc-build` links rc0 with the TU absent. Absence here is not a latent link error; it is an
  unreachable path. (Same distinction that made `Display.cpp` dead-by-non-reference rather than
  by collision.)
- `tools/sim-driver.cpp:46` includes `GameActionMoveTo.hpp` for `F3::GameActionWait`
  (`startMs`/`durationMs`/`Expired`), not for the mover TU — so the driver's green legs are not
  evidence that movement is exercised.

Adding both TUs to `target.F3` would therefore put code the image never calls into the shipped
exe, with no digest observable to justify the size/surface change and no paired `hp=`/`q=`/`pos=`
leg to prove it. Deleting is worse: both files carry the assertions that make the movement era
testable, and `run-all` would lose two rows' content.

**So the disposition is: declared gap, tracked, with inclusion gated on the thing that would
actually consume it** — Step 2's `QueueAnimEvent` / mover-clock work and the movement-era digest
legs. When a built TU first *needs* one of these symbols, that is the commit that registers it,
and the registration arrives with a digest pair to prove it, not as a housekeeping edit.

## Bound on this ruling (item 73, stated for positives too)

- "No built TU enqueues kind 1" covers the 42 TUs resolved from the two build lists at this HEAD.
  A future enqueue through a variable, table, or indirect dispatch is not excluded by this scan —
  it is a text search, not a call graph.
- The `virtual` reasoning excludes a *static* reference; it does not exclude a vftable emitted
  elsewhere. It explains `msvc-build` rc0 and nothing more.
- Which type words/paths the shipped demo actually drives is not statically enumerable, so
  "movement is dead in the demo" is NOT claimed. What is claimed: it is not reachable from the
  port's built image today.

## Why the tool exists

`build-orphan-check.py` classifies instead of counting and refuses a verdict when its own parse is
implausible (identity violation, empty listing, zero defs -> exit 2). Three of its first four
versions printed a confident PASS off a broken instrument, including one that filed a live shard
as "delete-or-absorb". The census is safe to act on only where the row prints its evidence type
and its in-flight status, which is why both are mandatory fields now.
