## Fixed: the camera's three layers (Gfx_CamCtrl / Gfx_CamCtrl_Orbit / CameraControl)

The layering defect recorded in the previous section is closed. F3's maps describe three objects, and
the port had collapsed them into one:

    CameraControl            vftptr +0x0, owner link +0x4, Gfx_CamCtrl_Orbit +0x8 (0xB8), own +0xC0..+0x120
    Gfx_CamCtrl_Orbit        : Gfx_CamCtrl, NO state of its own
    Gfx_CamCtrl              vftptr +0x0, byte +0x4, dwords +0x8..+0xB4, size 0xB8

`.?AVGfx_CamCtrl_Orbit@@` marks every one of its entries `base=True` - they are the base's fields
seen through the derived object, at CameraControl-ABSOLUTE offsets (+0x8 there is the orbit's own
+0x0). The port had re-declared sixteen of them inside the orbit and ten more inside CameraControl, so
the whole band landed after the embedded object: the azimuth triple that belongs at `+0xa4` was at
`+0xEC`.

Three defects fixed together:
- `Gfx_CamCtrl` was in EA order with a BYTE `mbr_0x4` first, i.e. the cls_0x50dbb0 rotation - now
  offset order, `virtual` for its recorded vftptr, size 0xB8;
- the orbit declared state it does not own - now member-less;
- `CameraControl` declared the orbit's band as its own - now it embeds the orbit and declares only
  `+0xC0..+0x11C`, size 288.

Two findings only the compiler could settle:
- the MODE REGISTER is a **dword at +0xC2 whose low half is the "zoom speed" slot at +0xC4** (the
  shipped code writes 32-bit through it). Declaring both separately made `sizeof` 0x124; a union of
  `dword mbr_0xc2` and `word mbr_0xc4w` gives the shipped overlap and 288.
- the azimuth/elevation/distance triple must be **float**. Declared as dwords the arithmetic read the
  bit pattern as an integer: `set_azimuth` computed `6e10` instead of `28.6`. That is what the probe's
  behavioural check caught - it pokes 0.5 rad at absolute `+0xa4`, calls `set_azimuth_0x585ea0(0.5 *
  57.295776f)` and requires the shipped early-out (anim bit 0 clear); an integer field fails it.

Call sites re-pointed from `mbr_0xa4/0xa8/0xac` to `mbr_0x8.mbr_0x9c/0xa0/0xa4` (abs - 8) in
CameraControl.cpp (22 uses) and src/F3/Commands.cpp (5 uses). Full suite: 24/24 OK.

## The defect class was systemic: 7057 members sit at an offset their own name contradicts

`tools/check-member-offsets.py --static` is new. The existing census only inspects member-name
ACCESSES in ported .cpp files, so a header that nothing touches yet is never checked - and
`Gfx_CamCtrl` was exactly that: EA-ordered, `byte mbr_0x4` first, every field one slot off, invisible
to the census. The static pass needs no access site: it compares each member's computed offset against
the offset its own name spells (`mbr_0x14` claims +0x14).

**First run: 7057 members in 702 files.** The generated headers list data members in IDA's EA
(alphabetical) order, which only accidentally matches offset order - and when a byte or a base-class
field is involved, declaration order moves every later field.

`tools/sort-member-decls.py --f3 --apply FILE...` fixes a file from F3 rather than from names: it
takes the fields F3 marks `base=False` (the class's OWN, not the base's) in offset order, keeps the
port's existing declaration text and comments for members that already existed, and inserts explicit
`byte pad_0xNN[n]` fillers where the order alone would leave a hole. It refuses classes it cannot
settle: overlapping shipped offsets (needs a union), a member size with no C type, an unresolved base,
packed classes.

Applied first to the Action family (11 classes). `ActionDie` is the pattern: it declared
`byte mbr_0x10, dword mbr_0x14, byte mbr_0x18, byte mbr_0x4` - EA order, and the last one is the
BASE's field (F3 marks it base=True), so the port put the base's byte at +0x11. Now: pad to +0x10,
byte, pad to +0x14, dword, byte.

Two things this iteration established that matter for the remaining 690 files:
- **F3 "size" is an extent, not `sizeof`.** `ActionDie` is 25 (0x19) there while MSVC's `sizeof` is
  0x1C because a class with a vftptr pads to 4. Verify member OFFSETS, not sizes.
- derived classes re-declare their base's fields (ActionDie did). That is the same duplicate-member
  defect as `net::buffer::overflow`, and F3's `base` flag is the authority for dropping them.

## Tree-wide reorder: 614 classes (static rows 7144 -> 3621)

`tools/sort-member-decls.py --f3 --apply` now rewrites the whole tree. Four things it got wrong on the
way, each caught by a different existing guard - worth recording, because every one of them looked
like success from the tool's own output:

1. **It emitted exactly F3's fields.** That silently DROPS port fields F3 does not list, and every use
   site fails with C2039. Now it reorders and pads only; the sole removal is a member F3 marks
   `base=True` AND the port's own base class actually declares (otherwise the field just vanishes).
2. **It ignored array counts.** `byte mbr_0x8[0xc]` counted as one byte, so eleven bogus filler bytes
   went in after it and the header's own `offsetof` guards failed with C2118.
3. **It reordered access specifiers.** `public:` is not a member; sorted into the middle of the block
   it makes the following fields private - C2248 at the first `cam.mbr_0x4` use.
4. **It trusted the parser's single-base model for multiple inheritance.** `GUI::Window : Base,
   HeapTracker` got filler pushed over a layout a human had already derived from the ctor. Classes
   with more than one base are skipped now.

The lesson across all four: the tool cannot verify itself (its padding step absorbs any gap, so
re-simulating it only confirms its own arithmetic). The real verifiers are the `offsetof` guards the
headers already carry and the suite - which is why every one of these was caught before landing.

Remaining 3621 rows in 144 files are classes the tool refuses: `//: Members` block/class pairing
mismatches, unresolved bases, shipped offset overlaps needing a union, and sizes with no C type.

## The last 3588 rows are NOT an ordering problem - they are class composition

Multiple-inheritance layouts are now modelled instead of skipped: bases sit in declaration order, each
at its own alignment, so a class's own fields begin after ALL of them
(`multi_base_start`). That unlocked 2 more classes and, more usefully, produced the diagnosis for
everything the tool still refuses.

Refusal census over the tree: **130 classes "member falls inside the base"**, 42 "base unresolved",
11 "multiple bases, one unsized".

The 130 are the flattened memory-image structs (`VFXEFFECTTYPE_PARTICLESYSTEM_Struct` and friends,
237 static rows each). They mix THREE base classes and then re-declare fields at offsets that lie
inside those bases:

    struct VFXEFFECTTYPE_PARTICLESYSTEM_Struct : VFXEFFECTTYPE_BASE_Struct, cls_0x50db20, cls_0x4dff90 {
        ... mbr_0x74 ...      // the bases already occupy 0x0..0x324

No declaration ORDER can put `mbr_0x74` at +0x74 when the bases start at +0x0 and run to +0x324.
F3 says why: it marks those members `base=True` - they belong to one of the base classes. The defect is
not that the fields are misordered, it is that they are attributed to the WRONG CLASS (the same defect
`net::buffer::overflow` and `CameraControl` had, one and two layers up).

So the remaining work for these files is a composition fix, not a reorder: move each `base=True`
member down into the base class that owns it, then re-run the reorderer on both classes. That needs a
per-hierarchy pass with the layout guards as the check - a different unit of work from the mechanical
sweep, and one that must not be done blind, because a wrong owner silently overlaps two objects.

## The header work lives in the NESTED repo - and the rewrite is now idempotent

Two process defects found the hard way this iteration, both worth as much as the code change:

**`modules/openje` is its own git repository.** Committing it from the parent (`git add modules/openje`)
records a submodule POINTER, not the file contents. Several iterations of header rewrites were staged
in the parent while the nested repo's worktree stayed dirty, and a routine `git -C modules/openje
checkout src` then discarded all of it. Header changes must be committed INSIDE `modules/openje` first
(commit c77b63a), and the parent commit only records which revision that is.

**A rewrite that is not idempotent is a churn machine.** Re-running the reorderer over a tree it had
already processed reported "616 classes would change" - because it re-read its own `pad_0xNN` fillers
as members and generated new padding around them. It now skips `pad_` members (the padding step
regenerates them), so a second run is a no-op. That check is part of the acceptance for this tool: a
transform that keeps rewriting the same declaration is the doorknob-polishing failure in mechanical
form, and it also makes every later diff unreadable.

Also added: a class-typed member whose span the OTHER declared members fully cover is a subobject the
header already flattens, so it is replaced by padding instead of being kept (keeping both put its
children after the whole subobject). Partial coverage is NOT flattened - that deletes state of its own
(CameraControl's embedded orbit, cls_0x401d60's fields).
