## Fixed: the camera's three layers (Gfx_CamCtrl / Gfx_CamCtrl_Orbit / CameraControl)

The layering defect recorded in the previous section is closed. F3's maps describe three objects, and
the port had collapsed them into one:

    CameraControl            vftptr +0x0, owner link +0x4, Gfx_CamCtrl_Orbit +0x8 (0xB8), own +0xC0..+0x120
    Gfx_CamCtrl_Orbit        : Gfx_CamCtrl, NO state of its own
    Gfx_CamCtrl              vftptr +0x0, byte +0x4, dwords +0x8..+0xB4, size 0xB8

`.?AVGfx_CamCtrl_Orbit@@` marks every one of its entries `base=True` - they are the base's fields
seen through the derived object, at CameraControl-ABSOLUTE offsets (+0x8 there is the orbit's own
+0x0). The port had re-declared sixteen of them inside the orbit and ten more inside CameraControl, so
the whole band landed after the embedded object: the azimuth triple that belongs at `+0xa4` was at
`+0xEC`.

Three defects fixed together:
- `Gfx_CamCtrl` was in EA order with a BYTE `mbr_0x4` first, i.e. the cls_0x50dbb0 rotation - now
  offset order, `virtual` for its recorded vftptr, size 0xB8;
- the orbit declared state it does not own - now member-less;
- `CameraControl` declared the orbit's band as its own - now it embeds the orbit and declares only
  `+0xC0..+0x11C`, size 288.

Two findings only the compiler could settle:
- the MODE REGISTER is a **dword at +0xC2 whose low half is the "zoom speed" slot at +0xC4** (the
  shipped code writes 32-bit through it). Declaring both separately made `sizeof` 0x124; a union of
  `dword mbr_0xc2` and `word mbr_0xc4w` gives the shipped overlap and 288.
- the azimuth/elevation/distance triple must be **float**. Declared as dwords the arithmetic read the
  bit pattern as an integer: `set_azimuth` computed `6e10` instead of `28.6`. That is what the probe's
  behavioural check caught - it pokes 0.5 rad at absolute `+0xa4`, calls `set_azimuth_0x585ea0(0.5 *
  57.295776f)` and requires the shipped early-out (anim bit 0 clear); an integer field fails it.

Call sites re-pointed from `mbr_0xa4/0xa8/0xac` to `mbr_0x8.mbr_0x9c/0xa0/0xa4` (abs - 8) in
CameraControl.cpp (22 uses) and src/F3/Commands.cpp (5 uses). Full suite: 24/24 OK.

## The defect class was systemic: 7057 members sit at an offset their own name contradicts

`tools/check-member-offsets.py --static` is new. The existing census only inspects member-name
ACCESSES in ported .cpp files, so a header that nothing touches yet is never checked - and
`Gfx_CamCtrl` was exactly that: EA-ordered, `byte mbr_0x4` first, every field one slot off, invisible
to the census. The static pass needs no access site: it compares each member's computed offset against
the offset its own name spells (`mbr_0x14` claims +0x14).

**First run: 7057 members in 702 files.** The generated headers list data members in IDA's EA
(alphabetical) order, which only accidentally matches offset order - and when a byte or a base-class
field is involved, declaration order moves every later field.

`tools/sort-member-decls.py --f3 --apply FILE...` fixes a file from F3 rather than from names: it
takes the fields F3 marks `base=False` (the class's OWN, not the base's) in offset order, keeps the
port's existing declaration text and comments for members that already existed, and inserts explicit
`byte pad_0xNN[n]` fillers where the order alone would leave a hole. It refuses classes it cannot
settle: overlapping shipped offsets (needs a union), a member size with no C type, an unresolved base,
packed classes.

Applied first to the Action family (11 classes). `ActionDie` is the pattern: it declared
`byte mbr_0x10, dword mbr_0x14, byte mbr_0x18, byte mbr_0x4` - EA order, and the last one is the
BASE's field (F3 marks it base=True), so the port put the base's byte at +0x11. Now: pad to +0x10,
byte, pad to +0x14, dword, byte.

Two things this iteration established that matter for the remaining 690 files:
- **F3 "size" is an extent, not `sizeof`.** `ActionDie` is 25 (0x19) there while MSVC's `sizeof` is
  0x1C because a class with a vftptr pads to 4. Verify member OFFSETS, not sizes.
- derived classes re-declare their base's fields (ActionDie did). That is the same duplicate-member
  defect as `net::buffer::overflow`, and F3's `base` flag is the authority for dropping them.

## Tree-wide reorder: 614 classes (static rows 7144 -> 3621)

`tools/sort-member-decls.py --f3 --apply` now rewrites the whole tree. Four things it got wrong on the
way, each caught by a different existing guard - worth recording, because every one of them looked
like success from the tool's own output:

1. **It emitted exactly F3's fields.** That silently DROPS port fields F3 does not list, and every use
   site fails with C2039. Now it reorders and pads only; the sole removal is a member F3 marks
   `base=True` AND the port's own base class actually declares (otherwise the field just vanishes).
2. **It ignored array counts.** `byte mbr_0x8[0xc]` counted as one byte, so eleven bogus filler bytes
   went in after it and the header's own `offsetof` guards failed with C2118.
3. **It reordered access specifiers.** `public:` is not a member; sorted into the middle of the block
   it makes the following fields private - C2248 at the first `cam.mbr_0x4` use.
4. **It trusted the parser's single-base model for multiple inheritance.** `GUI::Window : Base,
   HeapTracker` got filler pushed over a layout a human had already derived from the ctor. Classes
   with more than one base are skipped now.

The lesson across all four: the tool cannot verify itself (its padding step absorbs any gap, so
re-simulating it only confirms its own arithmetic). The real verifiers are the `offsetof` guards the
headers already carry and the suite - which is why every one of these was caught before landing.

Remaining 3621 rows in 144 files are classes the tool refuses: `//: Members` block/class pairing
mismatches, unresolved bases, shipped offset overlaps needing a union, and sizes with no C type.

## The last 3588 rows are NOT an ordering problem - they are class composition

Multiple-inheritance layouts are now modelled instead of skipped: bases sit in declaration order, each
at its own alignment, so a class's own fields begin after ALL of them
(`multi_base_start`). That unlocked 2 more classes and, more usefully, produced the diagnosis for
everything the tool still refuses.

Refusal census over the tree: **130 classes "member falls inside the base"**, 42 "base unresolved",
11 "multiple bases, one unsized".

The 130 are the flattened memory-image structs (`VFXEFFECTTYPE_PARTICLESYSTEM_Struct` and friends,
237 static rows each). They mix THREE base classes and then re-declare fields at offsets that lie
inside those bases:

    struct VFXEFFECTTYPE_PARTICLESYSTEM_Struct : VFXEFFECTTYPE_BASE_Struct, cls_0x50db20, cls_0x4dff90 {
        ... mbr_0x74 ...      // the bases already occupy 0x0..0x324

No declaration ORDER can put `mbr_0x74` at +0x74 when the bases start at +0x0 and run to +0x324.
F3 says why: it marks those members `base=True` - they belong to one of the base classes. The defect is
not that the fields are misordered, it is that they are attributed to the WRONG CLASS (the same defect
`net::buffer::overflow` and `CameraControl` had, one and two layers up).

So the remaining work for these files is a composition fix, not a reorder: move each `base=True`
member down into the base class that owns it, then re-run the reorderer on both classes. That needs a
per-hierarchy pass with the layout guards as the check - a different unit of work from the mechanical
sweep, and one that must not be done blind, because a wrong owner silently overlaps two objects.

## The header work lives in the NESTED repo - and the rewrite is now idempotent

Two process defects found the hard way this iteration, both worth as much as the code change:

**`modules/openje` is its own git repository.** Committing it from the parent (`git add modules/openje`)
records a submodule POINTER, not the file contents. Several iterations of header rewrites were staged
in the parent while the nested repo's worktree stayed dirty, and a routine `git -C modules/openje
checkout src` then discarded all of it. Header changes must be committed INSIDE `modules/openje` first
(commit c77b63a), and the parent commit only records which revision that is.

**A rewrite that is not idempotent is a churn machine.** Re-running the reorderer over a tree it had
already processed reported "616 classes would change" - because it re-read its own `pad_0xNN` fillers
as members and generated new padding around them. It now skips `pad_` members (the padding step
regenerates them), so a second run is a no-op. That check is part of the acceptance for this tool: a
transform that keeps rewriting the same declaration is the doorknob-polishing failure in mechanical
form, and it also makes every later diff unreadable.

Also added: a class-typed member whose span the OTHER declared members fully cover is a subobject the
header already flattens, so it is replaced by padding instead of being kept (keeping both put its
children after the whole subobject). Partial coverage is NOT flattened - that deletes state of its own
(CameraControl's embedded orbit, cls_0x401d60's fields).

## The ordering work is now gated, not just done: a ratchet, not a backlog

`tools/check-member-offsets.py --ratchet N` and a `layout-ratchet` step in
`devenv/scripts/run-all-tests.nix` enforce the contract that matters now:

> a change may REDUCE the number of members declared at an offset their own name contradicts, never
> raise it.

A "zero rows" gate would be wrong today - 3588 rows remain in the flattened memory-image structs, and
those need a composition fix, not an ordering one. But without a gate, the next hand-written header can
reintroduce exactly the defect class this campaign removed, and nothing would notice: the offsets stay
plausible (they are one dword or one padding slot off, not wild), the build succeeds, and the suite
passes because no test reads that member.

Demonstrated both directions on a throwaway edit to `ActionDie.hpp`:
- a comment-only edit leaves the count at 3588 - the gate tolerates harmless change;
- an EA-style "tidy" that moves the byte above the dword reports 3591 rows in 145 files and names
  `ActionDie::mbr_0x14 named +0x14 but laid out at +0x10` - it detects the regression, and exits 1
  when the count exceeds the ceiling (checked at ceiling 3587).

The ceiling is meant to be lowered as the backlog clears; it is a floor of protection, not an
acceptance target. Leaving it stale at 3588 while fixing files would be safe but sloppy, so the tool
prints "(lower the ceiling to N)" whenever it runs below the ceiling.

## Shipped overlaps: what MSVC 2002 accepts, and what it forbids

The refused classes that remain split into "shipped offset overlap" (two members the original
addresses at different widths over the same bytes, e.g. a dword at +0x70 and byte views at +0x72/+0x73)
and the flattened memory-image structs. Before writing a rewriter for the overlap case I asked the
shipped compiler instead of assuming - `tools/probes/probe_union_overlap.cpp`:

**Accepted.** An anonymous struct inside a union overlays exactly as intended:

    union { dword mbr_0x70; struct { word pad_0x70; byte mbr_0x72; byte mbr_0x73; }; };

Measured relative offsets 0x70->4, 0x72->6, 0x73->7 and `sizeof` 12 for that shape, with the byte
views reading the dword's own bytes (0xAABBCCDD -> 0xBB at the third byte). My first probe "failed"
only because I had written absolute offsets into a struct that starts at 0 - the compiler was right and
my expectation was wrong, which is the second time this campaign that lesson has paid.

**Forbidden.** MSVC 2002 rejects a union arm with a user-defined constructor:

    error C2620: member '...::mbr_0x34' of union '...::__unnamed' has user-defined constructor or
                 non-trivial default constructor

That matters because the wide arm in these VFX structs is exactly such a class (`cls_0x50db20`,
`cls_0x4dff90`). So a union can model a scalar overlap but never a class-subobject one.

**Consequence.** An attempt to emit unions automatically was written, measured and reverted: 58 classes
would have been rewritten and the build failed with C2620 in `VFXEFFECTTYPE_BASE_Struct` and
`VFX_EffectInstance`. The union path is therefore only valid where the wide member is a scalar; the
class-subobject case stays refused and needs the composition fix (move the children into the class
that owns them), not a layout trick. Reverting kept the tree at the 3588-row ratchet with the suite
green, which is the right trade: a layout feature that cannot run on the files that need it is not
progress.

## F3's `cls_0xNNNN_0xNN` subobject annotations can be fabricated - the dtor settles it

`VFXEFFECTTYPE_BASE_Struct` carried `cls_0x50db20 mbr_0x34` - a **577-byte** subobject. Its shipped
destructor at `0x4e1750` disposes exactly two members, both straight off `this`:

    cmp [esi+1Ch],10h / jb / mov eax,[esi+8]  / free / [+18h]=0 / [+1Ch]=0Fh / [+8]=0
    cmp [esi+4Ch],10h / jb / mov eax,[esi+38h] / free / [+48h]=0 / [+4Ch]=0Fh / [+38h]=0

Two SSO strings, ptr/size/capacity at `+0x8/+0x18/+0x1C` and `+0x38/+0x48/+0x4C` (threshold `0x10`,
capacity reset `0xF`) - the `cls_0x50db20` shape, but seen through `this`, not through a subobject. A
577-byte member starting at `+0x34` would contain `+0x38`, and this dtor could not free its pointer, so
no such subobject is there. `mbr_0x34` is 4 bytes, and F3's `cls_0x50db20_0x34` row is a fabricated
annotation - the same mistake as the orbit's derived-extent `size`.

That correction alone removed 11 static rows (ceiling lowered 3588 -> 3577) because the bogus size had
been blocking the class from being reordered at all: `mbr_0x38` "fell inside" a member that never
existed.

The class still refuses to reorder, and now for an honest reason: `cls_0x4dff90 mbr_0x54` (56 bytes per
F3) spans over `mbr_0x60`, so those two subobject rows also cannot both be right. Their types are the
next question - and the destructor does not touch them, so `mbr_0x54`/`mbr_0x60` need a different
witness before they are typed. Guessing there would silently overlap two objects, which is the failure
mode this audit exists to prevent.

### Correction: the ctor is the positive witness, the dtor alone is not

The section above claimed F3's `cls_0x50db20_0x34` row was fabricated because the dtor at `0x4e1750`
frees only `[+0x8]` and `[+0x38]`. **That was wrong, and the constructor disproves it** (`0x4e0f00`):

    lea ecx,[esi+2Ch] / call cls_0x502110__ctor_0x502110
    lea ecx,[esi+34h] / call cls_0x50db20__ctor_0x404bc0     <-- a subobject AT +0x34
    lea ecx,[esi+54h] / call cls_0x4dff90__ctor_0x523b00
    lea ecx,[esi+60h] / call JE__StringTree__ctor_0x52c260

The dtor reads the way it does because the subobject's own destructor was **inlined** into it: the
string it frees at `[+0x38]` is `subobject+0x4`. An inlined destructor looks exactly like a member of
the enclosing object, which is precisely the trap.

So the rule is asymmetric: `lea ecx,[esi+off] / call <class>::ctor` is positive proof of a subobject at
`off`; the absence of a matching destructor call proves nothing, because it may be inlined. The member
is restored (`cls_0x50db20 mbr_0x34`) and the ratchet ceiling is back at 3588 - the previous "11 rows
removed" were an artefact of the bad edit, not progress.

What the ctor does show for real: `[+0x8]` is an SSO string initialised **inline** (`[+0x1C]=0xF`,
`[+0x18]=0`, `[+0x8]=0`) with no ctor call, i.e. a plain string member occupying `+0x8..+0x20` whose
type the port still models as loose dwords. That is the next honest unit for this class.

## The port's std::string is 0x1C; the original's 0x18-byte string cannot be modelled with it

`VFXEFFECTTYPE_BASE_Struct`'s ctor (`0x4e0f00`) initialises a string member at `+0x8` **inline**:
`[+0x1C]=0xF` (capacity), `[+0x18]=0` (size), `[+0x8]=0` (buffer). That is an SSO string occupying
`+0x8..+0x20`, i.e. **0x18 bytes with size at member+0x10 and capacity at member+0x14** - the VC7.1
`std::string` shape built WITHOUT iterator debugging.

Which cannot be expressed in this port. `tools/probes/probe_stdstring_size.cpp` measures, under the
project's own compile flags:

    sizeof(std::string) = 0x1C      size at +0x14, capacity at +0x18

The extra 4 bytes come from the iterator-debugging container base and survive
`#define _HAS_ITERATOR_DEBUGGING 0` before the include (the build's PCH has already pulled in the STL).
So substituting `std::string mbr_0x8` makes the type 4 bytes too big and every later offset moves:
attempting exactly that failed the suite with C2118 and dropped the static-check census to 2223 - a
number that looks like progress and is really the tool mis-sizing the member. Reverted; rows back to
3588.

Two durable consequences:

- **No offset-named member in the port may be typed `std::string`** (`grep -c 'std::string mbr_'` = 0
  today). It is 4 bytes larger than the original's string, so it silently shifts everything after it.
  Where the port currently models such a member as loose dwords (`mbr_0x8`, `mbr_0x18`, `mbr_0x1c`) it
  is at least the right SIZE, which is why those classes still pass their offset guards.
- Modelling the string properly needs a dedicated 0x18-byte type whose ctor/dtor match the original's
  (capacity reset `0xF`, threshold `0x10`, `free` on overflow) - a real unit of work, not a keyword
  substitution.

## `JE::StringSSO16` - the engine's 0x18-byte string, now a real type

Since this build's `std::string` is 0x1C and the original's string is 0x18 (measured, previous
section), the size-correct type now exists as `modules/openje/src/JE/StringSSO16.hpp`:

    union { char buf[0x10]; char* ptr; };   // +0x0  text inline, or heap pointer
    unsigned size;                          // +0x10
    unsigned capacity;                      // +0x14  SSO while < 0x10

Every field comes from the shipped code, not from a header guess: the ctor at `0x4e0f00` writes
`[+0x1C]=0xF`, `[+0x18]=0`, `[+0x8]=0`, and the dtor at `0x4e1750` branches on `[+0x1C] < 0x10` before
freeing `[+0x8]` - so the 16 bytes at the member start ARE the text while capacity is small.

The layout is pinned by `offsetof` typedefs asserting `sizeof == 0x18`, `size` at `0x10` and `capacity`
at `0x14`. Falsified on purpose: widening `buf` to 0x14 makes the very next suite build fail with
C2118, so the pin is live rather than decorative.

`VFXEFFECTTYPE_BASE_Struct` now declares `StringSSO16 mbr_0x8` instead of three loose dwords
(`mbr_0x8`, `mbr_0x18`, `mbr_0x1c` were that string's pointer/buffer, size and capacity). Static rows
3588 -> 3586.

This does NOT make the port string-complete: only the layout is modelled. Appending, growing, copying
and freeing live in the free functions already ported in `cls_0x50db20.cpp` (`0x4256E0`, `0x4257D0`,
`0x425BD0`), which operate on this layout; wiring them into a class interface is separate work, and
inventing method semantics before that would be guesswork.
