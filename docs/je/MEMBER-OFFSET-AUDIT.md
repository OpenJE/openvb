## Why this is a defect class and not a style question

`modules/openje/src/JE/CSound.hpp` declares `mbr_0x100, mbr_0x104, ..., mbr_0x115,
mbr_0x1c, ... mbr_0x3c, mbr_0x4, mbr_0x40 ...` - IDA's EA order. C++ assigns offsets in
DECLARATION order, so in that class `mbr_0x4` lives at +0x3C. `CSound.cpp:256` does
`ResourceSystem* rs = (ResourceSystem*)this->mbr_0x4;` and then calls through the result:
it reads whatever sits at +0x3C and treats it as a vtable-bearing object.

`cls_0x420270 : public cls_0x41cff0` declares only `mbr_0x28` and `mbr_0x2c`, so they land at
+0x4/+0x8 while the code (and the shipped bytes) mean +0x28/+0x2c: the class is missing the
members in between. Same effect, different cause - the census reports both, because both make
a member NAME address the wrong word.

## How the detector was validated

1. **Against known-true cases.** The three defects already fixed by hand were re-introduced in
   a disposable copy (`/tmp/audit-selftest`, never the live tree) and the detector named the
   files again: `net/base.cpp` (+0x48) and `net/critical_section.cpp` (+0x4). With those fixes
   present in the live tree, neither file is reported.
2. **Against a false positive it had to lose.** `net/base.cpp`'s own explanatory comment
   contains the text `this->mbr_0x48`; the first version of the detector counted it as an
   access. The tool now blanks comments before scanning, which also stopped a comment
   containing the word `virtual` from making `net::socket` look polymorphic.

## Correction: the net::socket "third defect" of the previous iteration was NOT one

Commit `ef505a5` changed `net::socket::meth_0x5b8d40` from `this->mbr_0x4` to an explicit
`(byte*)this + 0x4` and claimed the original read the vftable word at +0x0, so
`closesocket()` got a vtable pointer and every real socket stayed open.

That claim is **wrong**, and the evidence is a measurement: `socket` declares
`virtual undefined4 virt_deldtor_0x59d500()`, so the compiler inserts the vftptr at +0x0 and
puts `mbr_0x4` at exactly +0x4 - the member access was correct. Compiling the PRE-fix
`socket.cpp` (`git show ef505a5^:src/JE/net/socket.cpp`) against the same probe passes all
seven checks, including "the descriptor was actually closed by WinSock" and "the +0x0 word is
untouched". The "mutant" that failed five checks had replaced the access with `(int*)this` -
an expression the shipped code never contained, i.e. the result proved nothing about the
original.

The change itself is harmless (explicit offset, identical codegen) and is kept, but its commit
message must not be read as evidence of a fixed bug. `ef505a5` is not rewritten - it is
retracted here.

## What the 251 rows are

Ranked by file, `ActionAnim.cpp` (19) and `Client.cpp` (23) are the largest single offenders;
every row is a candidate, not a proven bug: a class whose member list is complete and whose
base is sized correctly is flagged only when the shipped offset really differs, but a class

That is what the row-by-row burn-down has to establish.
