## Fixed so far

| class | defect | how it was caught |
|---|---|---|
| `net::base` | `meth_0x59d530` read `mbr_0x48`, which the header puts far from +0x48, so the +0x48 release never fired | probe armed the slot with a recording deleting-dtor and watched it stay at 0 |
| `net::critical_section` | `dtor_0x5b92a0` read `mbr_0x4`, not at +0x4, and passed garbage to `DeleteCriticalSection` then `free` | the chain faulted inside ntdll the first time it was driven end to end |
| `JE::ActionAnim` | members were declared in EA order AND the struct re-declared `byte mbr_0x4`, hiding `Action`'s flag, so the ctor wrote the flag at +0x20 and every named member sat 8..12 bytes early | compile-time `offsetof`/`sizeof` assertions against the F3 DB member map (sizeof 40, own members from +0x10, base flag at +0x4) |

The ActionAnim fix is the template for the rest: pin the layout with compile-time assertions
rather than trusting the name, because a wrong offset compiles cleanly and runs silently.

## What the detector can and cannot see

It reports a row only when it could size the whole class: base class resolved and every member
type known. 72 of the 1000 parsed classes are therefore skipped (their bases are not in the
parsed set or hold types it cannot size), and their accesses are never flagged - silence about
a class is not a clean bill of health for it. It also cannot see the second ActionAnim cause at
all: a re-declared base member hides the base's field without changing any offset that a name
lookup would notice; only the compile-time assertion caught that.

## Correction: the net::socket "third defect" of an earlier iteration was NOT one

Commit `ef505a5` changed `net::socket::meth_0x5b8d40` from `this->mbr_0x4` to an explicit
`(byte*)this + 0x4` and claimed the original read the vftable word at +0x0, so
`closesocket()` got a vtable pointer and every real socket stayed open.

That claim is **wrong**, and the evidence is a measurement: `socket` declares
`virtual undefined4 virt_deldtor_0x59d500()`, so the compiler inserts the vftptr at +0x0 and
puts `mbr_0x4` at exactly +0x4 - the member access was correct. Compiling the PRE-fix
`socket.cpp` (`git show ef505a5^:src/JE/net/socket.cpp`) against the same probe passes all
seven checks, including "the descriptor was actually closed by WinSock" and "the +0x0 word is
untouched". The "mutant" that failed five checks had replaced the access with `(int*)this` -
an expression the shipped code never contained, i.e. the result proved nothing about the
original. `ef505a5` is not rewritten; it is retracted here.
